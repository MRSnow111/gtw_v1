# План: документы в чате, проекты и просмотр готовых файлов

Статус: **план (не реализация)**. Три связанные возможности:
- **A. Документы «в чат и из чата»** — пользователь загружает файл агенту и скачивает результат.
- **B. Проекты** — именованные рабочие пространства, группирующие чаты и файлы.
- **C. Просмотр готового файла** — открыть код / презентацию / PDF прямо в интерфейсе.

Подход — MVP сначала, потом итерации (как договаривались). Ниже: что уже есть, общий
фундамент, дизайн каждой фичи, фазы, безопасность и открытые вопросы.

офиса**. Всё это надстраивается без правки ядра.

## 1. Общий фундамент: единый файловый реестр + отдача

Одна подсистема обслуживает и загрузку (A), и артефакты (A/C), и файлы проекта (B).

### 1.1 Таблица `files`
```sql
CREATE TABLE IF NOT EXISTS files (
  id           TEXT PRIMARY KEY,          -- "f_<uid>"
  login        TEXT NOT NULL,             -- владелец (изоляция)
  chat_id      TEXT,                      -- NULL = файл уровня проекта
  project_id   TEXT,                      -- NULL = без проекта
  name         TEXT NOT NULL,             -- исходное имя (санитизированное)
  mime         TEXT NOT NULL DEFAULT '',
  size         INTEGER NOT NULL DEFAULT 0,
  direction    TEXT NOT NULL,             -- 'upload' (user→agent) | 'artifact' (agent→user)
  storage_path TEXT NOT NULL,             -- абсолютный хостовый путь
  preview_path TEXT,                      -- кэш PDF-рендера (для офиса), NULL пока нет
  created_at   TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_files_login ON files (login, created_at);
CREATE INDEX IF NOT EXISTS idx_files_chat  ON files (chat_id);
CREATE INDEX IF NOT EXISTS idx_files_proj  ON files (project_id);
```

### 1.2 Хранилище
- Каталог `GTW_DATA_DIR/files/<login>/<fileId>/<name>` — владеет `server.js` (тот же
  `gtw.service`, пользователь `hermes`). Отдача и проверка владельца — здесь.
- Чтобы агент увидел загруженный файл, адаптер **копирует** его в песочницу профиля:
  `~/.hermes/sandboxes/docker/gtw-<login>/home/uploads/<chat>/<name>` → внутри песочницы
  это `/root/uploads/<chat>/<name>` (bind-mount). Копия дешёвая, зато хранение/отдача
  остаются за server.js, а доступ агента — через его штатный `/root`.

### 1.3 HTTP-маршруты (вариант: Next API routes `app/api/files/*`)
Кука проверяется тем же `src/lib/authToken.ts`, что и остальные роуты.
- `POST /api/files` — multipart, поле `file` (+ `chat_id?`, `project_id?`). Лимит размера,
  allowlist типов, санитизация имени → сохраняет, регистрирует в `files`, возвращает
  `{id, name, mime, size, url}`.
- `GET /api/files/<id>` — проверка владельца (`login` из куки == `files.login`; админ может
  всё), отдача потока. `Content-Disposition: inline` для просмотра / `attachment` для
  скачивания (`?download=1`). Поддержка `Range` (PDF/видео). `Content-Type` из `mime`.
- `GET /api/files/<id>/preview` — отдаёт `preview_path` (PDF-рендер), если есть; иначе 404
  (фронт тогда запрашивает рендер, см. C).
- `DELETE /api/files/<id>` — владелец/админ; удаляет запись + файл (+ рендер).

Альтернатива — обработчик прямо в `server.js` (лучше для стриминга больших файлов и
`Range`); Next API routes проще и консистентнее с существующими `/api/*`. **Решить на
старте реализации**; для MVP подойдут Next routes с лимитом ~25 МБ.

### 1.4 Безопасность (сквозная)
- Только владелец (или админ). Никаких произвольных хостовых путей — отдача строго по `id`
  из реестра, `storage_path` нормализуется и проверяется на выход за корень хранилища.
- Санитизация имени (`clean_attachment_filename`-подобная), запрет `..`, абсолютных путей.
- Лимит размера на файл и суммарная квота на пользователя (защита диска).
- Allowlist MIME/расширений; исполняемые/скрипты принимаются как файлы, но не исполняются
  сервером. Отдача с корректным `Content-Type` + `X-Content-Type-Options: nosniff`.
- Изоляция профилей сохраняется: файл копируется только в песочницу своего профиля.

## 2. Фича A — документы «в чат и из чата»

### 2.1 Загрузка (пользователь → агент)
1. `Composer.addFile()` в live: реальный `<input type=file>` + drag-drop → `POST /api/files`
   (прогресс через `XMLHttpRequest.upload.onprogress`), чипы `uploading→ready/failed` (UI уже есть).
2. При отправке сообщения `user_message` получает поле `attachments: [{fileId,name,mime}]`
   (только id — пути клиент не знает).
3. `server.js::gateClientFrame` для `user_message`: проверяет, что каждый `fileId`
   принадлежит логину, и пробрасывает кадр (login уже подставляется из куки).
4. Адаптер `_inbound_message`: для каждого вложения копирует файл в песочницу профиля и
   строит `MessageEvent(text=…, media_urls=[путь], media_types=[mime], media_filenames=[name])`.
   Ядро само инлайнит текст / даёт vision-доступ к картинкам.
   - **Открытый вопрос:** конвенция пути host vs sandbox для `media_urls` (ядро инлайнит
   текст на хосте, vision читает в песочнице). Проверить на реализации; при необходимости
   адаптер транслирует путь. Для текста можно передавать хостовый путь, для картинок —
   путь, видимый vision-инструменту.

### 2.2 Артефакт (агент → пользователь)
1. `send_document`/`send_image` вместо сырого пути: регистрируют файл в `files`
   (`direction='artifact'`, копируют/ссылаются на песочницу), вычисляют `name/mime/size` и
   шлют расширенный кадр:
   ```json
   {"type":"artifact","chat_id":"…","id":"f_…","kind":"document|image|code",
    "name":"report.pdf","mime":"application/pdf","size":12345,
    "url":"/api/files/f_…","caption":"…"}
   ```
2. `liveStore` case `artifact`: сохраняет `id/name/mime/size/url`, определяет `kind` по MIME
   (код/картинка/pdf/офис/текст). `ArtifactPanel` показывает реальную кнопку «Скачать»
   (`url?download=1`) и «Открыть» (просмотр, фича C).
3. Совместимость: старые кадры без `id` фронт обрабатывает как раньше (деградация без ошибки).

### 2.3 Объём MVP фичи A
Реестр `files` + `POST/GET /api/files` + реальная загрузка в Composer + `attachments` в
`user_message` + копирование в песочницу и `media_urls` в адаптере + расширенный кадр
артефакта + рабочая кнопка «Скачать». Просмотр картинок/кода уже есть.

## 3. Фича B — проекты

Проект = именованное пространство: группирует чаты, имеет общую папку файлов и рабочий
каталог в песочнице. Изоляция per-user сохраняется (проекты внутри профиля пользователя).

### 3.1 Данные
```sql
CREATE TABLE IF NOT EXISTS projects (
  id         TEXT PRIMARY KEY,           -- "p_<uid>"
  login      TEXT NOT NULL,
  name       TEXT NOT NULL,
  slug       TEXT NOT NULL,              -- для каталога в песочнице, уникален в рамках login
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  archived   INTEGER NOT NULL DEFAULT 0
);
CREATE TABLE IF NOT EXISTS chats (
  chat_id    TEXT PRIMARY KEY,
  login      TEXT NOT NULL,
  project_id TEXT,                       -- NULL = чат без проекта
  title      TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL,
  last_activity TEXT
);
```
`files.project_id` / `files.chat_id` уже есть (фундамент). existing-чаты мигрируются в
`chats` с `project_id=NULL`.

### 3.2 API (Next routes `app/api/projects/*`, `app/api/chats/*`)
- `GET/POST /api/projects`, `PATCH/DELETE /api/projects/<id>` (rename/archive/delete;
  delete — только владелец, каскадно отвязывает чаты/файлы, не удаляя их).
- `POST /api/chats` (создать чат в проекте), `PATCH /api/chats/<id>` (перенос/имя).
- Все роуты — проверка владельца по куки.

### 3.3 UI
- Сайдбар: секция «Проекты» (создать/переименовать/архив/удалить), чаты сгруппированы под
  проектом; «новый чат в проекте». Чаты без проекта — отдельная группа.
- Панель файлов проекта (вкладка в `ArtifactPanel` или отдельная) — `files` с
  `project_id`, загрузка уровня проекта.
- Хлебные крошки / заголовок активного проекта.

### 3.4 Контекст агента
- Рабочий каталог проекта в песочнице: `/root/projects/<slug>/` (хост
  `…/gtw-<login>/home/projects/<slug>/`). Файлы проекта кладутся туда.
- Адаптер при ходе чата проекта добавляет в контекст рабочий каталог и (позже) инструкции
  проекта. MVP: агент получает путь каталога и список файлов проекта; дальше — per-project
  инструкции/память.

### 3.5 Объём MVP фичи B
Таблицы `projects`/`chats` + CRUD API + группировка чатов в сайдбаре + создание чата в
проекте + папка проекта в песочнице. Инструкции проекта и перенос существующих чатов — итерация.

## 4. Фича C — просмотр готового файла

Расширяем `ArtifactPanel` + полноэкранный модал просмотра. Рендер по типу:

| Тип | Рендер | Зависимости |
|---|---|---|
| Код/текст | `CodeViewer` (есть), добавить определение языка по расширению | — |
| Markdown | рендер в HTML (лёгкий парсер) | small md-lib |
| Картинка | `<img>` + lightbox (есть) | — |
| PDF | `<iframe>`/`<object>` или `pdf.js` | нативно / pdf.js |
| Офис (pptx/docx/xlsx) | **конвертация в PDF через LibreOffice** (уже в образе) → PDF-просмотр | soffice в песочнице |

### 4.1 Офис → PDF: два пути
- **MVP (без отдельного сервиса):** кнопка «Открыть как PDF» шлёт обычное сообщение агенту
  «сконвертируй `<file>` в PDF и пришли» — агент делает `soffice --headless --convert-to pdf`
  в песочнице и шлёт PDF-артефакт. Использует существующий поток, но тратит ход/токены.
- **Итерация (мгновенный просмотр):** отдельный WS-кадр `render_request {file_id}` → адаптер
  запускает `soffice` в песочнице профиля **без LLM-хода** (one-off команда через
  docker-окружение профиля), кэширует PDF в `files.preview_path`, шлёт
  `render_ready {id, preview_url}`. Фронт показывает PDF. Требует от адаптера исполнение
  команды в песочнице вне хода — аккуратно, с таймаутом и кэшем.

### 4.2 Кадр артефакта для просмотра
Расширенный кадр (см. 2.2) несёт `mime`/`kind`/`url`/`preview_url?`. Фронт выбирает рендер по
`mime`. Для офиса без готового рендера — кнопка «Открыть как PDF» (MVP) / авто-рендер (итерация).

### 4.3 Объём MVP фичи C
Нативные просмотрщики код/текст/markdown/картинка/PDF + рабочая кнопка «Открыть» у
артефакта + офис через конвертацию агентом по запросу. Мгновенный рендер офиса отдельным
кадром — итерация.

## 5. Фазы (MVP → итерации)

**Фаза 1 — файловый фундамент + документы (A MVP).**
Реестр `files`, `POST/GET/DELETE /api/files`, реальная загрузка в Composer, `attachments` в
`user_message`, копирование в песочницу + `media_urls` в адаптере, расширенный кадр
артефакта, рабочая кнопка «Скачать». *Результат: файл можно загрузить агенту и скачать результат.*

**Фаза 2 — просмотр (C MVP).**
Просмотрщики код/текст/md/картинка/PDF, кнопка «Открыть», офис→PDF по запросу через агента.
*Результат: готовый код/PDF/презентация открывается в интерфейсе.*

**Фаза 3 — проекты (B MVP).**
Таблицы `projects`/`chats`, CRUD API, группировка чатов в сайдбаре, папка проекта в
песочнице, файлы уровня проекта. *Результат: проекты с чатами и общими файлами.*

**Итерации (потом):**
- Мгновенный рендер офиса отдельным кадром `render_request` (без LLM-хода).
- Инструкции/память проекта, per-project модель по умолчанию.
- Перенос существующих чатов в проекты, массовые операции с файлами.
- Стриминг больших файлов / `Range` в server.js, квоты диска, превью-кэш.
- Версионирование файлов, поиск по проектам.

Порядок нарочно такой: A даёт фундамент (реестр/отдача), на котором стоят и C, и B.

## 6. Безопасность и ограничения (чек-лист)
- Владение: каждый файл/проект/чат проверяется по `login` из подписанной куки; админ — всё.
- Path traversal: отдача только по `id` из реестра; нормализация + проверка корня хранилища.
- Лимиты: размер файла, суммарная квота на пользователя, allowlist типов.
- Отдача: корректный `Content-Type`, `nosniff`, `Content-Disposition`; ничего не исполняется.
- Изоляция профилей: копия только в песочницу своего профиля; токен браузеру не выдаётся.
- Квота токенов: загрузка файла не обходит `user_limits`; ход с вложением гейтится как обычно.
- WS-протокол остаётся JSON-текстовым; бинарные файлы идут через HTTP, не через WS.

## 7. Риски / открытые вопросы
1. **Путь `media_urls` host vs sandbox** — ядро инлайнит текст на хосте, vision читает в
   песочнице. Проверить конвенцию на старте A; при необходимости адаптер транслирует путь.
2. **Провижининг песочницы для нового пользователя** — каталог профиля создаётся на первом
   ходе. Загрузка файла до первого хода: либо создать каталог заранее, либо класть в реестр и
   копировать при первом ходе. Решить (MVP: копия при ходе, файл ждёт в реестре).
3. **Рендер офиса вне хода** (итерация C) — исполнение команды в песочнице из адаптера без
   LLM-хода; нужны таймаут, кэш, обработка «контейнер не запущен».
4. **Миграция чатов** — существующие чаты без персистентной таблицы; аккуратный бэкфилл `chats`.
5. **Большие файлы** — Next routes имеют лимит тела; для >25 МБ перенос в server.js со стримингом.
